# v0.6 — Browser guest-memory prototype

**Status:** independent sparse Wii RAM address-space adapter and smoke test. This is not yet the upstream runtime Memory implementation.

## Implemented
- MEM1: 24 MiB; MEM2: 128 MiB.
- Physical, cached, and uncached Wii address windows resolve to the same backing pages.
- 4 KiB pages allocate only on first write, avoiding a 152 MiB startup allocation.
- 8-, 16-, and 32-bit reads/writes use PowerPC big-endian byte order.
- Invalid addresses fail safely.
- Startup smoke test covers aliasing, endianness, bounds, sparse allocation, and reset.

## Differences from upstream
Upstream translated code can use a fixed 4 GiB host virtual-address reservation, direct pointer biases, page protection, and fault handlers for MMIO, deferred reads, and executable writes. Those mechanisms are not available in WebAssembly in the same form.

This adapter deliberately uses checked accessors and sparse pages. It is a foundation for a WASM-compatible memory contract, not a drop-in replacement for upstream Memory, MemoryInline, or GuestFlat. It does not implement MMIO, deferred EFB reads, executable write guards, fast translated-code pointers, or guest CPU execution.

## Next steps
1. Compare address translation against upstream Wii memory region and alias rules.
2. Add cross-page and boundary tests.
3. Design MMIO and deferred-read behavior without host page-fault interception.
4. Integrate game-independent runtime code only after its memory contract can target this adapter.
