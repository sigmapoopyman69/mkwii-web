# v0.5 — Runtime porting notes

**Status:** first host-context prototype implemented; this is not yet the upstream game runtime.

## Why this is a port, not a build-flag change

The upstream [WiiCompiled runtime](https://github.com/patchzyy/Wiicompiled/tree/main/runtime) is a native desktop application. Its runtime CMake configuration rejects Emscripten, requires a 64-bit Clang desktop target, and pulls in Aurora plus desktop host dependencies. The project also has a separate Aurora submodule.

The web project currently builds only its small browser diagnostics executable. It does not compile upstream runtime sources or translated game code.

## First component: cooperative host contexts

Upstream's guest scheduler uses a small `HostContext` interface:

- initialize and shut down the scheduler context;
- create and destroy guest execution contexts;
- identify the currently active context;
- switch between contexts.

The native implementations use Windows Fibers, libco, or a small macOS assembly backend. Those implementations cannot be used directly in WebAssembly.

This milestone adds an independent Emscripten implementation under `src/platform/browser_host_context.*`. It maps the same basic operations onto Emscripten's cooperative-fiber API:

- each context has a C stack and an Asyncify stack;
- the original browser/main context is captured as the scheduler;
- switching is cooperative and stays on the browser main thread;
- a smoke test performs two context round-trips during WASM startup.

Emscripten fibers require Asyncify instrumentation. The build therefore enables `-sASYNCIFY`. This is an experiment to validate one important runtime primitive, not proof that the complete WiiCompiled scheduler is compatible.

## Portability audit

| Upstream subsystem | Browser issue | Direction |
|---|---|---|
| HostContext / guest fibers | Native Fibers, libco, and assembly are unavailable | Emscripten fibers prototype; validate stack and scheduler semantics |
| Guest flat memory | Reserves a fixed 4 GiB host virtual-address region and uses page-protection fault handlers | Replace with bounded WebAssembly linear-memory addressing and explicit MMIO/deferred-read checks |
| Aurora graphics | Native windowing and desktop GPU backends | Separate GX command translation from presentation; build a WebGPU backend |
| AudioBackend | SDL audio streams | Feed the existing guest audio mixer into Web Audio with browser-safe buffering |
| Controller input | SDL controllers and native Bluetooth paths | Browser Gamepad API adapter; omit native Bluetooth host support |
| DVD/NAND storage | Native filesystem paths and synchronous reads | Async browser file access plus a deliberate guest-I/O scheduling bridge |
| Networking | Native sockets and platform TLS | Browser-supported networking only; redesign socket HLE around browser restrictions |
| Runtime startup/config | Native executable paths, process APIs, files, and desktop UI | Browser lifecycle, IndexedDB-backed configuration, and DOM UI |

## Non-goals for this first slice

- Do not import the full upstream runtime yet.
- Do not compile or publish translated game code or game assets.
- Do not treat a successful fiber smoke test as a playable game.
- Do not enable pthreads/shared memory by default. The current site reports shared memory as unavailable, and Emscripten fiber continuations are thread-specific.

## Next gates

1. Prove the Emscripten context backend under the project's pinned Emscripten SDK.
2. Port and test guest memory using WebAssembly linear memory rather than native 4 GiB virtual-memory tricks.
3. Define asynchronous browser file I/O semantics before adapting DVD/NAND HLE.
4. Bring up a small, game-independent slice of upstream runtime code only after its memory and scheduling dependencies are understood.
5. Integrate GX, audio, and input incrementally; only then consider translated-code integration.
