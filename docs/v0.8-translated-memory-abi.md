# WiiCompiled Web v0.8 — Translated-memory helper ABI

## Goal

Start adapting the memory interface used by WiiCompiled's generated C++ without pretending the native translated runtime can already run in WebAssembly.

## Implemented

- Adds a process-wide browser guest-memory instance for translated code to share.
- Provides checked implementations using the upstream helper spellings: `MemoryInline::FlatRead8/16/32/64`, `FlatReadFloat32/64`, and matching write helpers.
- Includes the `FlatWriteRam*` helper family used by codegen for stores proven to target ordinary RAM.
- Invalid and unmapped accesses latch a runtime fault instead of silently treating a bad read as valid zero data.
- Adds a startup smoke test that executes a small generated-code-style C++ block through these helper names, including aliases and a fault case.

## Important limitations

This is a transitional ABI prototype, not a drop-in implementation of upstream `memory_access.h`. It does not provide the upstream page tables, direct host pointers, 4 GiB flat reservation, deferred framebuffer reads, MMIO/HLE handling, executable-write guards, or the full translator/runtime. The helper subset is checked and slower by design. The float32 store currently uses a normal C++ narrowing conversion; upstream's hardware-specific PowerPC conversion still needs to be ported before real translated code can rely on it.

The current smoke-test block is hand-written C++ shaped like emitted code. It is not a translated game function and contains no game data.

## Next steps

1. Port the remaining helper semantics, especially PowerPC float conversion, MMIO policy, and access-fault reporting.
2. Add a translator output mode that emits these checked helper calls rather than raw flat pointers.
3. Compile a tiny synthetic PowerPC instruction block through the upstream translator and run its generated C++ under Emscripten.
4. Only after that works, integrate more runtime services and user-supplied game builds locally; do not upload game dumps or generated game content.
