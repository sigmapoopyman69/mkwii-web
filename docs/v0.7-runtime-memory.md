# WiiCompiled Web v0.7 — Runtime memory API adapter

## Goal

Move the v0.6 sparse MEM1/MEM2 model toward the memory contract used by the upstream runtime, without pretending the translated-code engine is already browser-compatible.

## Implemented

- Checked 8-, 16-, 32-, and 64-bit integer access.
- 32- and 64-bit floating-point access, preserving the guest's PowerPC big-endian representation.
- Range validation for multi-page reads and writes.
- Bulk copies between guest memory and host buffers.
- A smoke test for cross-page 64-bit access, physical/cached/uncached aliases, floating-point values, bulk copies, and invalid ranges.

## Deliberate differences from upstream

The upstream Memory API is static and includes GetPointer, deferred reads, region registration, and other runtime behavior. Its translated-code layer (MemoryInline) expects a fixed 4 GiB guest address space and direct host pointers. Upstream's GuestFlat also relies on OS virtual-memory reservations and page protections to trap MMIO, deferred framebuffer reads, unmapped accesses, and writes to executable pages.

WebAssembly linear memory cannot reproduce those native virtual-address and page-protection assumptions directly. This milestone therefore exposes only checked operations; it does not return raw guest pointers, implement MMIO, or run translated code.

## Next integration gates

1. Design a browser-compatible replacement for pointer-based translated loads/stores (likely generated access helpers or a WebAssembly-memory offset ABI).
2. Define MMIO and deferred-read callbacks without native access-violation handlers.
3. Adapt upstream host-context scheduling and guest CPU context ownership.
4. Only then attempt to compile selected upstream runtime components behind explicit browser platform interfaces.

No game data, translated game code, or game assets are included.
